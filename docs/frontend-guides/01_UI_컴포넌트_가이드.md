# UI 컴포넌트 가이드

## 1. 목적

이 문서는 새 화면이나 컴포넌트를 만들 때 기존 디자인 시스템과
일관성을 유지하기 위한 규칙을 정리한다.

---

## 2. 기존 컴포넌트 인벤토리

새 화면을 만들기 전에 아래 목록에서 재사용 가능한 컴포넌트가 있는지
먼저 확인한다. 없으면 만들고, 있으면 그대로 가져다 쓴다.

### `src/components/ui/`

| 컴포넌트         | 용도                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- |
| `Button`         | variant(primary/outline/destructive/link/ghost) × size(default/lg/sm)                   |
| `IconButton`     | 아이콘 전용 원형 버튼, variant(default/ghost) × size(default/lg/sm)                     |
| `Input`          | layout(default/label-left/with-button), 라벨/에러/헬퍼텍스트 지원                       |
| `AuthCard`       | 480px 흰 카드 + 중앙 타이틀. 로그인/회원가입류 화면 뼈대                                |
| `ConfirmDialog`  | "삭제하시겠습니까?" 류 확인 모달 (취소/확인 버튼)                                       |
| `CompleteDialog` | 완료 안내 모달 (원형 아이콘 + 제목 + 설명 + CTA 버튼)                                   |
| `RoleBadge`      | `FestivalOwnerBadge`(총괄관리자)/`OperatorBadge`(운영자)/`StaffBadge`(스태프) 역할 뱃지 |
| `checkbox`       | shadcn 기반 체크박스. 목록 다중 선택(운영자/스태프 관리 화면)에 사용                    |
| `Bottombar`      | 화면 하단 액션 바. type(default: 취소/등록 · selected: N개 선택됨/삭제)                 |

### `src/components/layout/`

| 컴포넌트    | 용도                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| `Header`    | variant(default/signup/login) — 공개 페이지 CTA 또는 콘솔 유저 메뉴             |
| `Nav`       | 콘솔 상단 5개 탭 네비게이션                                                     |
| `HeaderNav` | Header(login)+Nav를 간격 없이 결합한 콘솔 상단바 — 콘솔 화면은 이걸 통째로 쓴다 |

새 모달/폼 카드가 필요하면 `ConfirmDialog`/`CompleteDialog`/`AuthCard`를
직접 확장하지 말고, 값이 다르면 새 props를 추가하는 방향으로 먼저 검토한다.

---

## 3. 아이콘

아이콘은 `@radix-ui/react-icons`만 사용한다. 커스텀 SVG를 새로 그리거나
다른 아이콘 라이브러리(lucide 등)를 섞어 쓰지 않는다.

`components.json`에 `shadcn` CLI가 설치돼 있고 `iconLibrary: lucide`로
잡혀 있지만, 이건 향후 `npx shadcn add <component>`로 개별 컴포넌트를
가져올 때를 위한 설정일 뿐이다. 아이콘은 여전히 Radix로 통일한다.

---

## 4. 색상·타이포그래피 토큰

`src/app/globals.css`에 정의된 토큰만 사용한다. Tailwind 기본 팔레트나
raw 폰트 크기 클래스를 쓰지 않는다.

금지:

```text
text-gray-500
text-sm font-semibold
text-lg font-semibold
```

권장:

```text
text-zinc-500
body-small-bold
heading-small
```

주요 토큰:

- 색상 스케일: `zinc-50`~`zinc-950`, `red-300/500/600`,
  `primary-300/500/600`, `secondary-300/500/600`, `point-300/500/600`
- 시맨틱 별칭: `primary`(=`primary-600`, 블루 `#236CF6`) /
  `secondary`(=zinc-700) / `error`(=red-500) / `dimmed`(=zinc-950 25%)
  — **`primary`는 zinc-900이 아니라 블루다.** 버튼 primary variant,
  input focus 링, 액티브 nav 탭 텍스트 등이 전부 이 값을 따라간다.
  로고처럼 `primary` 변경에 영향받으면 안 되는 곳은 `text-zinc-900`처럼
  직접 색을 지정해 분리한다(`Header`의 "축지법" 로고가 그 예).
- 역할 뱃지 색: 총괄관리자(`FESTIVAL_OWNER`) = `primary-600`,
  운영자(`SUB_ADMIN`) = `secondary-600`(`#007CFF`), 스태프 = `point-600`
  (`#FD7E14`). 총괄관리자/운영자 두 색이 육안으로 비슷해 보이니 직접
  클래스를 새로 짓지 말고 `RoleBadge`의
  `FestivalOwnerBadge`/`OperatorBadge`/`StaffBadge`를 재사용한다.
- 타이포: `heading-large/regular/small`,
  `body-large/regular/small/caption`(-bold 변형 포함)

새 색상이 필요하면(디자이너가 Figma에서 새 hex를 준다면) 먼저
`globals.css`의 `@theme inline` 블록에 토큰으로 추가하고, 컴포넌트에서는
그 토큰만 참조한다. 컴포넌트 파일에 hex를 직접 쓰지 않는다.

이 프로젝트는 **라이트 모드 전용**이다. `prefers-color-scheme: dark`
미디어 쿼리를 다시 추가하지 않는다.

## 5. 인증 화면(로그인/회원가입/비밀번호 찾기·재설정) 레이아웃

- `Header` + `<main className="bg-dimmed grid flex-1 grid-cols-3 items-center gap-6 p-8">` 구조로
  통일한다. 폼은 `flex items-center` 등으로 뷰포트 중앙에 직접 배치하지 않고,
  3-컬럼 그리드의 **가운데 컬럼**(`<div className="col-start-2 flex justify-center">`)에
  넣는다 — 콘솔 화면(`ConsoleLayout`)과 같은 그리드 규칙을 공개 페이지에도 맞춘 것이다.
- 폼 카드는 `AuthCard`(480px, `p-8`=32px 패딩, 자동 높이)를 쓴다.
  특정 화면만 다른 고정 크기가 필요하다는 명시적 지시가 없는 한
  고정 `h-[...]` 값을 넣지 않는다.
- 완료 안내(회원가입 완료, 비밀번호 변경 완료 등)는 페이지 인라인이
  아니라 `CompleteDialog` 모달로 띄운다.
- 서브텍스트(타이틀 아래 설명 문구)는 `text-zinc-500`이 아니라
  `text-zinc-950`을 쓴다 — 이 프로젝트의 인증 화면 규칙.

---

## 6. 컴포넌트 export 규칙

`Button`/`Input`처럼 Props 타입과 variant/size 타입은 항상 `export`한다.
새 UI 컴포넌트를 추가할 때 `ComponentProps`, `ComponentVariant`,
`ComponentSize` 형태의 타입을 export 안 하고 넘어가지 않는다.

모듈 레벨 스타일 상수(여러 variant/size를 매핑하는 `Record<...>`)는
`SCREAMING_SNAKE_CASE`로 이름 짓는다. 예: `SIZE_STYLES`, `VARIANT_STYLES`.

## 7. 화면 폭 — 고정 px 대신 비율 클래스

디자이너가 콘솔 화면을 화면 전체(뷰포트) 기준 3등분으로 설계한다.
헤더/하단 버튼바처럼 가장자리까지 꽉 채우는 chrome은 전체(3/3)를 쓰고,
폼·상세 같은 콘텐츠 카드는 그중 일부(예: 2/3)만 차지한다.

이 비율은 **고정 픽셀(`max-w-[790px]`)이 아니라 `w-1/3`/`w-2/3`/`w-full`
같은 비율 클래스로 구현한다** — 고정 px는 화면 폭이 바뀌면 더 이상
"전체의 2/3"이 아니게 되어 반응형이 깨진다.

```text
금지: max-w-[790px]
권장: w-2/3
```

`ConsoleLayout`(`src/app/console/layout.tsx`)은 콘텐츠 영역에 별도
최대폭 컨테이너를 두지 않고 좌우 여백(`px-10`)만 준다 — 그래서 "화면
전체의 2/3"과 "이 여백 안쪽 영역의 2/3"이 사실상 같다. 향후 콘텐츠
전체를 감싸는 최대폭 컨테이너(예: `mx-auto max-w-[1440px]`)가
추가되면, 그때는 비율을 뷰포트가 아니라 그 컨테이너 기준으로
다시 검토해야 한다.

새 폼/상세 화면을 만들 때 폭을 정해야 하면, 먼저 Figma에서 그 영역이
전체 대비 몇 등분인지 확인하고 그 비율 클래스를 쓴다. 애매하면
디자이너에게 확인한다 — 눈대중으로 px 값을 추정해서 넣지 않는다.
