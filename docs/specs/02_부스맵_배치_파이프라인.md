# 부스맵 자동 배치 파이프라인

- 저장 일시: 2026-07-23
- 저장 목적: 배치도 이미지 업로드부터 사용자 서비스 반영까지의 전체 파이프라인을 단계별로 정리하고, 프론트엔드(`chookjibupAdmin_FE`)가 담당하는 범위를 명확히 한다.
- 문서 상태: 팀에서 공유된 흐름도를 그대로 옮긴 초안이다. 각 단계의 실제 API 계약, 처리 방식(동기/비동기), 데이터 스키마는 아직 미확정이다.
- 관련 문서: [`01_기능명세서.md`](./01_기능명세서.md)의 `축제 부스맵 수정` 항목

## 전체 흐름

| #   | 단계                                                 | 담당                                     |
| --- | ---------------------------------------------------- | ---------------------------------------- |
| 1   | 배치도 이미지 업로드                                 | 프론트엔드 (업로드 UI)                   |
| 2   | S3 저장                                              | 백엔드                                   |
| 3   | OpenCV 이미지 보정 (왜곡 보정, 노이즈 제거)          | 백엔드/AI 파이프라인                     |
| 4   | OCR 텍스트 인식 (부스명, 화장실, 출입구 등)          | 백엔드/AI 파이프라인                     |
| 5   | SAM2 영역 추출 (부스, 길, 건물, 공터 등 영역 분리)   | 백엔드/AI 파이프라인                     |
| 6   | Vision AI + 규칙 기반 객체 분류 (무슨 시설인지 판단) | 백엔드/AI 파이프라인                     |

| 11  | AI 대기열 최적화 실행                                | 백엔드/AI 파이프라인                     |
| 12  | 사용자 서비스에 반영                                 | 백엔드 → `chookjibupUser_FE`             |

        ↓

        ↓

        ↓

## 프론트엔드 담당 범위 (`/console/festivals/[festivalId]/boothmap`)

### 1단계 — 배치도 이미지 업로드

- 이미지 파일 선택/드래그 앤 드롭 업로드 UI
- 업로드 즉시 2~7단계(백엔드 파이프라인)가 시작되므로, 업로드 완료 후 "처리 중" 상태로 전환
- 프론트 TODO: 업로드 API가 파일을 직접 받는지, presigned URL을 먼저 발급받아 S3에 올리는 방식인지 확정 필요

### 2~7단계 — 백엔드 파이프라인 대기

- 프론트는 이 구간을 직접 처리하지 않고, 처리 상태만 조회한다
- UI 상태: 처리 중(스피너/진행률), 처리 실패(재시도 유도), 처리 완료
- 프론트 TODO: 처리 완료 확인 방식 확정 필요 — polling(`GET .../boothmap/status`)인지 WebSocket/SSE 알림인지에 따라 데이터 페칭 전략이 달라진다. 처리 시간이 길 경우(수 초~수십 초) polling 간격도 함께 정해야 한다.

### 8단계 — React-Konva 자동 배치 렌더링

- 7단계에서 생성된 도메인 객체 JSON을 받아 `react-konva` 캔버스에 초기 렌더링
- 객체 타입(부스/길/건물/공터/화장실/출입구 등)별로 서로 다른 도형·스타일 매핑 필요
- 프론트 TODO: `react-konva`, `konva` 패키지가 아직 설치되어 있지 않다. 도메인 객체 JSON 스키마(좌표 형식, 객체 타입 enum)가 확정되면 타입 정의와 함께 설치한다.

### 9단계 — 운영자 수정

- 자동 배치 결과 위에서 운영자가 직접 위치/크기/라벨을 수정
- 필요 기능 후보: 드래그 이동, 리사이즈, 객체 타입 재분류, 객체 추가/삭제, 실행 취소(undo)
- 프론트 TODO: 편집 히스토리(undo/redo) 지원 여부, 다중 선택 편집 지원 여부 확정 필요

### 10단계 — 최종 JSON 저장

- 운영자가 "저장" 액션을 실행하면 편집된 캔버스 상태를 도메인 객체 JSON으로 직렬화해 백엔드에 전송
- 저장 이후 11단계(AI 대기열 최적화)가 백엔드에서 트리거된다고 가정 — 프론트는 저장 완료 응답만 받고, 최적화 완료 여부는 별도 확인이 필요할 수 있음
- 프론트 TODO: 저장을 수동 버튼으로 할지, 편집 중 자동 저장(autosave)을 병행할지 확정 필요

## 11~12단계 (참고, 프론트 직접 구현 범위 아님)

- AI 대기열 최적화 실행과 사용자 서비스(`chookjibupUser_FE`) 반영은 백엔드/AI 파이프라인이 처리한다
- `chookjibupAdmin_FE`에서는 최적화 결과를 대시보드(`/console/festivals/[festivalId]/dashboard`)에서 조회하는 형태로 연결될 가능성이 있다 (기능명세서의 "축제 운영 AI 제안" 항목과 연결 검토 필요)

## 남은 확정 필요 사항

- 도메인 객체 JSON 스키마 (객체 타입, 좌표/크기 형식, 필수 속성)
- 업로드 방식 (직접 업로드 vs presigned URL)
- 2~7단계 처리 상태 확인 방식과 예상 처리 시간
- 편집 히스토리(undo/redo), 자동 저장 여부
- 11단계 완료 시점을 프론트에서 어떻게 알 수 있는지 (알림/polling 여부)

## 실제 구현 상태 확인 (2026-07-31, `demoAdmin_BE` `feat/booth-map-operations` 브랜치 코드 직접 확인)

이 문서가 작성된 2026-07-23 시점에는 위 12단계가 "팀에서 공유된 흐름도"였을 뿐 실제 구현은 없었다. 이후 백엔드가 부스·배치도 관련 기능을 구현했는데, **실제 코드는 이 문서의 2~7단계 설계와 다르다.** 상세 근거와 API 스펙은 [`03_부스맵_에디터_구현계획.md`](./03_부스맵_에디터_구현계획.md)에 정리했고, 여기서는 이 문서의 단계 번호에 맞춰 무엇이 바뀌었는지만 요약한다.

| #    | 이 문서의 설계                | 실제 구현 (코드 확인)                                                                                                                                                                                                              |
| ---- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 배치도 이미지 업로드 (프론트) | ❌ 업로드 API 자체가 없음. `MapCommandController`는 서버 classpath에 미리 박아둔 "고정 테스트 이미지" 하나만 분석 가능 (`storageType != TEST_RESOURCE`면 즉시 예외)                                                                |
| 2    | S3 저장                       | ❌ 없음. S3/파일 스토리지 연동 코드 전무                                                                                                                                                                                           |

| 4    | OCR 텍스트 인식               | ❌ 없음                                                                                                                                                                                                                            |
| 5    | SAM2 영역 추출                | ❌ 없음                                                                                                                                                                                                                            |

**PDF 지원 여부:** 이 문서와 별개로 팀에서 "PNG/JPG/PDF 업로드 → 방향·해상도 확인 → PDF는 페이지별 PNG 변환" 안이 공유됐으나, 실제 코드(`OpenAiMapImageAnalyzer.mimeType()`)는 PNG/JPG만 허용하고 PDF는 예외를 던진다. 이 안 역시 아직 구현 전 설계 단계다.

**결론:** 이 문서의 1·8·9·10단계(프론트 담당)는 여전히 유효한 설계지만, 2~7단계는 실제로 훨씬 단순하게(OpenAI 호출 1회) 구현됐고 그마저도 실사용자 이미지가 아닌 고정 테스트 이미지만 대상으로 한다. 실사용 가능한 업로드·분석 파이프라인을 만들려면 백엔드에 S3 업로드, 실이미지 분석 지원이 먼저 추가돼야 한다.
