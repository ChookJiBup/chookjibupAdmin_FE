## 3. 지금은 서버에 저장되지 않는 것 (한계)

`demoAdmin_BE`의 `FestivalBooth` 엔티티(`command/domain/FestivalBooth.java`) 필드는 `id, publicId, festivalId, name, category, location(자유 텍스트), description, operatingStatus, currentQueueLineId, expectedWaitingMinutes`뿐이고 **`x`/`y`/`width`/`height` 좌표 필드가 없다.** `CreateBoothRequest`/`UpdateBoothRequest`/`BoothResponse`도 동일하다. 따라서:

| 화면에서 되는 동작 | 서버 반영 여부 |
| --- | --- |
| 부스 드래그 이동 | ❌ 새로고침하면 원상복구 |
| 모서리 리사이즈 | ❌ 새로고침하면 원상복구 |
| Delete 삭제 | ❌ 화면에서만 제거, 서버 데이터 그대로 (삭제 API 자체도 없음) |
| 대기열 선 그리기 | ⚠️ `BoothQueueLine.pathData`/`entryPointData` 필드는 있으나 타입이 검증 없는 `String`이라 좌표 단위·좌표계 원점을 아직 합의하지 못함 |
| "최적 배치 제안" | ❌ 코드베이스에 배치 최적화 관련 로직 자체가 없음 (`optim`/`placement`/`layout` grep 0건) |

## 4. 백엔드에 요청하는 사항

1. **`FestivalBooth`에 위치·크기 컬럼 추가** (`x`, `y`, `width`, `height` — `rotation`은 요구사항에 없으면 생략 검토). 또는 대안으로 `MapObject`에 `boothId` 연결 필드를 추가해 "확정 지도 객체 = 부스 위치"로 재사용하는 방식도 가능 — 저장 방식은 백엔드 설계 재량에 맡긴다.
2. **`DELETE /api/festivals/{festivalId}/booths/{boothId}` 추가** — 현재 부스 삭제 API가 없다 (생성/수정만 존재).
3. **`BoothQueueLine.pathData`/`entryPointData`의 좌표 단위·좌표계 원점 확정** — 절대 px인지 캔버스 크기 대비 비율(0~1)인지, 예시 값(`120`, `80`)만으로는 프론트에서 단정할 수 없다.
4. **`feat/booth-map-operations` 브랜치의 `main` 병합 일정** 공유.
5. **"배치 최적화 제안" 기능의 요구사항 정의 여부 확인** — 현재 백엔드 코드/설계 어디에도 없는 완전 신규 기능이다. 무엇을 기준으로 최적화할지(동선 최소화? 혼잡도 분산?)부터 기획이 필요하다.

## 5. 프론트 다음 단계 (참고용)

1번 요청이 반영되면 곧바로 부스 위치 저장을 실 API로 교체할 수 있는 상태로 Phase 0을 마쳐뒀다. 3번(대기열 선 좌표 규격)이 확정되면 대기 라인 생성/수정 API 연동도 먼저 진행 가능하다. 상세 단계별 계획은 [`03_부스맵_에디터_구현계획.md`](./03_부스맵_에디터_구현계획.md)의 Phase 1~4 참고.
