- 저장 목적: 백엔드 기능명세를 라우트/화면/상태 관점으로 재설계해 프론트엔드 구현 기준으로 삼는다.
- 문서 상태: 라우트 스캐폴딩(`feat: scaffold route structure for 관리자/운영자/스태프`)에 맞춰 작성한 임시 정리본이다. API 계약이 확정되면 요청/응답 형식, 에러 처리 기준을 다시 정리한다.

## 역할과 라우트 그룹

| 역할                    | 진입 라우트                 | 레이아웃             | 비고                                            |
| ----------------------- | --------------------------- | -------------------- | ----------------------------------------------- |
| 관리자(총괄관리자 포함) | `/login` → `/console/*`     | `console/layout.tsx` | 회원가입은 `/signup`                            |
| 운영자                  | `/login` → `/console/*`     | `console/layout.tsx` | 계정은 관리자와 동일 테이블, 축제별 권한만 다름 |
| 스태프                  | `/staff/login` → `/staff/*` | `staff/layout.tsx`   | 회원가입 없음, 발급받은 계정으로만 로그인       |

관리자와 운영자는 계정 자체가 아니라 축제별 권한 관계로 구분되므로, 프론트에서도 "역할"을
전역 상태가 아니라 **선택된 축제(festivalId) 컨텍스트에 종속된 값**으로 다뤄야 한다.
같은 로그인 세션이라도 A 축제에서는 총괄관리자 UI, B 축제에서는 운영자 UI를 보여줘야 할 수 있다.

## 프론트 확정 필요 사항 (백엔드 API 계약과 별개로 프론트에서 결정할 것)

- ~~인증 토큰 저장 위치~~ → **결정(2026-07-23)**: `demoAdmin_BE`가 로그인 응답 바디로 JWT를 내려주고 CORS/쿠키 설정이 없어, httpOnly 쿠키 방식은 백엔드 변경 없이는 불가능하다. 대신 zustand `persist`(localStorage)로 토큰을 보관하고 axios 요청 인터셉터에서 `Authorization: Bearer` 헤더로 첨부한다. 개발 환경 CORS 문제는 `next.config.ts`의 `rewrites()`로 `/api/admin/*`, `/api/field-staff/*`를 백엔드로 프록시해 same-origin으로 우회했다 (`BACKEND_ORIGIN` 환경변수, 기본값 `http://localhost:8080`).
- ~~axios 인스턴스 분리 여부~~ → **결정**: 관리자/운영자용 `adminApiClient`(`/api/admin`)와 스태프용 `staffApiClient`(`/api/field-staff`)로 분리했다. 각각 자신의 zustand 스토어(`adminAuthStore`/`staffAuthStore`)에서 토큰을 읽어 헤더에 붙이고, 401 응답 시 해당 세션을 초기화한다.
- ~~라우트 가드 방식~~ → **결정**: httpOnly 쿠키가 없어 Edge `middleware.ts`에서 인증을 판단할 수 없으므로, 클라이언트 컴포넌트 가드(`AdminAuthGuard`/`StaffAuthGuard`)로 처리한다. `console/layout.tsx`에는 적용했지만 `staff/layout.tsx`는 `/staff/login`도 함께 감싸는 구조라 레이아웃 대신 `staff/dashboard/page.tsx` 등 보호가 필요한 개별 페이지에 가드를 건다.
- 축제별 권한(총괄관리자/운영자)을 어느 시점에 조회해 UI 분기(버튼 노출 등)에 반영할지 — `console/festivals/[festivalId]` 진입 시 권한 조회 API를 별도로 호출해야 함 (아직 미구현)
- 폼 검증 라이브러리 사용 여부 (회원가입/축제등록/스태프등록 등 입력 폼이 다수) — 로그인 폼은 우선 `required` 속성 정도의 최소 검증만 붙였다
- 로딩/빈 상태/에러 상태의 공통 컴포넌트화 여부 (로그인 폼은 `getApiErrorMessage`로 백엔드 에러 메시지를 그대로 노출하는 수준까지만 구현)
- Access Token 갱신 전략 — 현재 백엔드 로그인 응답에 refresh token이 없다. `expiresIn`(기본 1800초) 경과 후 재로그인을 요구할지, refresh 엔드포인트가 추가될지 백엔드와 확인 필요

## 화면별 명세

### `/` — 랜딩

- 역할: 전체
- 목적: 관리자/운영자 로그인과 스태프 로그인으로 분기하는 진입 화면
- 상태: 정적 화면, API 연동 없음

### `/signup` — 관리자 회원가입

- 백엔드 기능: 관리자 회원가입
- 역할: 관리자(운영자도 동일 절차)
- 입력 폼: 이메일, 이름, 조직, 비밀번호, 비밀번호 확인
- 클라이언트 검증: 이메일 형식, 허용 도메인(정부/공공기관, 개발 중 `naver.com` 임시 허용 가능성 — 운영 배포 전 제거 필요), 비밀번호 일치 여부
- 플로우: 이메일 인증코드 발송 → 인증코드 확인 → 나머지 정보 입력 → 가입 완료 (다단계 폼이 필요할 수 있음)
- UI 상태: 인증코드 발송 대기/재발송 타이머, 인증 실패, 이메일 중복 에러
- 프론트 TODO: 인증코드 재발송 주기, 인증 유효 시간 만료 시 UX 확정

### `/login` — 관리자/운영자 로그인

- 백엔드 기능: 관리자 로그인
- 역할: 관리자, 운영자 (계정 단위로는 구분 없음)
- 입력 폼: 이메일, 비밀번호
- 결과: JWT 발급 → `/console/festivals`로 이동
- 주의: 로그인 응답에는 축제별 권한이 없다. 로그인 직후에는 "총괄관리자/운영자"를 알 수 없고, 축제 목록·상세 조회 시점에 권한이 드러난다.
- UI 상태: 인증 실패(이메일/비밀번호 불일치), 탈퇴(`DELETED`) 계정 로그인 시도 에러

- 목적: 로그인 계정이 총괄관리자 또는 운영자로 연결된 축제를 진행예정/진행중/진행완료로 분류해 표시
