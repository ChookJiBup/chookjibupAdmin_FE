## 1. 한 줄 결론

**사용자가 요청한 "부스를 드래그로 옮기고 크기를 바꿔서 서버에 저장"하는 에디터는 지금 상태로는 완성할 수 없다.** 이유: `FestivalBooth` 엔티티에 좌표/크기를 저장하는 컬럼이 하나도 없다. 대기 라인(`BoothQueueLine`)의 경로 데이터, AI가 분석한 지도 객체(`MapObject`)는 좌표를 갖고 있지만, 이 셋은 서로 연결되어 있지 않다.

## 2. 백엔드 도메인별 실제 상태 (코드 인용)

### 2.1 `FestivalBooth` — 좌표 필드 없음

`src/main/java/com/example/demoadmin/booth/command/domain/FestivalBooth.java`의 전체 필드:

```
id, publicId, festivalId,
name, category, location(자유 텍스트, 예: "A구역 1번"),
description, operatingStatus,
currentQueueLineId, expectedWaitingMinutes
```

`x`, `y`, `width`, `height`, `rotation` 중 어느 것도 없다. `CreateBoothRequest`/`UpdateBoothRequest`/`BoothResponse` (`api/booth/dto/*.java`)도 동일하게 `name`/`category`/`location`/`description`만 주고받는다. `location`은 "A구역 1번" 같은 사람이 읽는 텍스트일 뿐 좌표가 아니다.

**의미:** 지금 부스를 캔버스에서 드래그해서 옮기거나 리사이즈해도, 그 결과를 저장할 API 필드 자체가 없다. 새로고침하면 사라진다.

### 2.2 `BoothQueueLine` — 좌표 있음, 단 검증 없는 문자열

`CreateBoothQueueLineRequest`/`UpdateBoothQueueLineRequest`:

```
lineOrder, label, expectedWaitingMinutes, maxCapacity,
pathData: String   예시 "[{\"x\":120,\"y\":80}]"
entryPointData: String   예시 "{\"x\":120,\"y\":80}"
```

`pathData`/`entryPointData`는 **타입이 `String`**이다. 백엔드는 이 값을 파싱하거나 검증하지 않고 그대로 저장·반환한다(Map 응답으로 변환하는 `MapObjectResponse.geometry`와 달리, `BoothQueueLineResponse.pathData()`는 문자열 그대로 반환).

**의미:** 대기 라인의 "경로(줄 서는 선)"는 원하는 JSON 구조로 저장할 수 있다. 다만 좌표 단위(px인지 %인지)는 백엔드가 정해주지 않으므로 프론트-백엔드가 별도로 합의해야 하고, 형식이 틀려도 저장 시점엔 에러가 안 난다(조회하는 쪽에서 파싱 실패로 터짐).

### 2.3 `MapObject` — AI 분석 전용, 부스와 무관

`MapObjectResponse` (`api/map/dto/MapObjectResponse.java`):

```
objectId, type, name, geometry: {x,y,width,height} (0~1 정규화), confidence, reviewStatus, source
```

이 객체는 **부스와 연결되는 `boothId` 필드가 없다.** 그리고:

- 생성/수정/승인 API가 없다. 존재하는 API는 `POST /maps/test-analysis`(분석 실행)와 `GET /maps/{mapId}/objects`(조회) 두 개뿐이다.
- `MapCommandController`에 `@ConditionalOnProperty(name = "app.map.analysis.test-endpoint-enabled", havingValue = "true")`가 붙어 있어, 이 플래그가 꺼져 있으면(운영 환경 기본값) 컨트롤러 자체가 스프링 빈으로 등록되지 않는다 → 404.
- `test-analysis`는 파일을 받지 않는다. 코드 주석 그대로 "김밥축제 테스트 이미지로 분석 저장 흐름을 실행"하는 **고정 픽스처**다. 사용자가 올린 이미지를 분석하지 않는다.

**의미:** "AI가 배치도를 분석해서 지도에 뿌려주는" 기능은 로컬 개발 환경 데모로만 가능하고, 그 결과를 실제 부스로 확정하는 절차도 없다.

**실제 분석 로직 (`OpenAiMapImageAnalyzer.java` 직접 확인):** 팀에서 공유된 "PDF→PNG 변환 → OpenCV 보정 → OCR → SAM2" 파이프라인은 코드에 없다. 실제로는 이미지를 base64로 인코딩해 OpenAI Responses API에 프롬프트("배치도 분석해서 JSON으로 반환해라", 허용 type/geometry enum 지정)와 함께 통째로 보내고, 응답 JSON을 파싱해 저장하는 **단일 API 호출**이 전부다. PDF는 `mimeType()`에서 바로 예외 처리되어 지원하지 않는다. [`02_부스맵_배치_파이프라인.md`](./02_부스맵_배치_파이프라인.md)의 "실제 구현 상태 확인" 표에 단계별 대조를 정리해뒀다.

### 2.4 "최적 배치 제안" AI — 백엔드에 해당 기능 자체가 없음

사용자가 공유한 이미지의 "AI는 [최적 배치] 버튼을 눌렀을 때만 동작"은 **배치 최적화 제안**을 뜻한다. 이는 `MapAnalysisApplicationService`가 하는 일(이미지에서 기존 시설을 인식하는 컴퓨터 비전 작업)과 **완전히 다른 기능**이다. 코드베이스 전체에서 "배치 최적화/제안" 관련 서비스·컨트롤러를 찾아봤으나 없다.

```bash
grep -rn "optim\|placement\|layout" src/main/java --include="*.java" -i
# → 매치 없음 (관련 코드 없음)
```

**의미:** 이 기능은 백엔드에 신규 기획·설계가 필요한 완전히 새로운 요구사항이다. 현재 있는 AI 분석 파이프라인을 재활용할 수 없다.

## 4. 기술 스택 — 그대로 채택 가능

사용자가 제시한 스택(React + react-konva + Zustand + TanStack Query)은 `chookjibupAdmin_FE`의 `package.json`에 **이미 전부 설치돼 있다** (`konva`, `react-konva`, `zustand`, `@tanstack/react-query`). `src/features/boothmap/BoothMapCanvas.tsx`도 이미 만들어져 있어 새 라이브러리 도입 없이 그 위에 이어서 만들면 된다.

역할 분담(Zustand=선택객체/도구/확대비율/Undo-Redo, react-konva=렌더링, TanStack Query=서버 통신)도 기존 프로젝트 관례와 어긋나지 않는다.

## 5. 단계적 구현 계획

### Phase 0 — 프론트 전용 에디터 골격 (지금 바로 시작 가능)

- 좌측 시설 팔레트, 캔버스, 우측 속성 패널 레이아웃
- 부스 클릭/드래그/리사이즈/삭제/자동 스냅/확대축소/Undo-Redo — 전부 Zustand 로컬 상태로만 구현
- 저장 버튼은 있지만 실제로는 `localStorage` 또는 메모리에만 저장 (서버 API 없음을 화면에 명시)
- `mockPipeline.ts`의 좌표계를 0~1 정규화로 맞춰 나중에 실좌표 API가 와도 스케일 계산을 다시 안 짜도 되게 함

### Phase 1 — 대기 라인만 실 API 연동

- 부스 생성/수정/조회, 대기 라인 생성/수정/조회, 줄 끝 갱신은 지금 바로 실 API로 교체 가능 (`api/booth/*`)
- 캔버스에서 그린 대기줄 경로를 `pathData`/`entryPointData`로 직렬화해 저장 — 단, 이 시점에 백엔드와 좌표 단위(px vs 0~1)와 좌표계 원점을 문서로 합의해야 함(현재 백엔드 예시는 `{"x":120,"y":80}` 같은 절대값으로 보임)

### Phase 2 — 부스 좌표 저장을 백엔드에 요청 (선행 조건)

Phase 0의 결과를 실제로 영속화하려면 아래 중 하나가 먼저 추가되어야 한다.

- (권장) `FestivalBooth`에 `x`, `y`, `width`, `height` 컬럼 추가 (`rotation`은 요구사항에 없으면 생략 검토)
- 또는 `MapObject`에 `boothId` 연결 필드를 추가하고 "확정 지도 객체 = 부스 위치"로 재사용
- `DELETE /api/festivals/{festivalId}/booths/{boothId}` 추가 (현재 삭제 API 없음)

### Phase 3 — 배치도 이미지 업로드 연동 (백엔드 로드맵 11절 항목)

- S3 업로드 API가 나오면 `BoothMapUploadPanel`의 mock을 실제 업로드로 교체
- `test-analysis`가 아닌 실사용자 이미지 분석 API가 나오면 `mockUploadAndProcess()`를 실제 폴링/조회로 교체

### Phase 4 — "최적 배치 제안" (완전 신규 기능, 별도 기획 필요)

- 백엔드에 이 기능이 아직 설계조차 안 되어 있으므로, 먼저 "무엇을 기준으로 최적화하는지"(동선 최소화? 혼잡도 분산?) 요구사항부터 백엔드·기획과 정의해야 함
- 프론트는 버튼 UI와 "서버 응답으로 좌표 일괄 갱신" 로직만 준비해두고 대기

## 6. 백엔드에 요청할 사항 (정리)

1. `FestivalBooth`에 위치/크기 컬럼 추가 여부 결정 (Phase 2)

4. `feat/booth-map-operations` 브랜치의 `main` 병합 일정
5. "배치 최적화 제안" 기능의 요구사항 정의 여부 확인 (아직 이 문서/코드 어디에도 없음)

## 7. 남은 확인 필요 사항

- `pathData`/`entryPointData`의 좌표계가 정규화(0~1)인지 절대 픽셀인지 — 백엔드 예시 값(`120`, `80`)만으로는 단정 불가, 백엔드 담당자 확인 필요
- 부스 삭제 API가 정말 없는지, 아니면 이번 브랜치에 아직 안 들어간 것인지
- Phase 2의 좌표 컬럼을 `FestivalBooth`에 직접 넣을지 별도 테이블(`BoothLayout`)로 분리할지는 백엔드 설계 재량이므로 여기서는 "무엇이 필요한지"만 요청하고 "어떻게 저장할지"는 백엔드에 맡긴다
